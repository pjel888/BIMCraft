# Practical workflow for future agents

1. Read the current user task, these setup notes and the inherited root `CLAUDE.md`. Locate applicable ancestor/nested `AGENTS.md` and `CLAUDE.md` files before editing the affected area. Inspect `README.md`, `Cargo.toml`, relevant `docs/areas/` notes and the nearest crate instructions. Reference repositories have their own instructions and licenses.
2. Inspect the exact repository root, branch, remotes, commit and working tree. Account for human edits and agree one writer for the affected files. Preserve uncommitted work; do not reset, discard, overwrite unrelated files or force push. For future changes, use a focused `codex/<scope>` branch unless instructed otherwise.
3. Distinguish inherited behavior, a proposal and a verified result. Define one useful package and acceptance evidence. Reuse the command/session architecture where suitable; do not introduce frameworks, services or cross-project code copies without an observed need and the task's authority.
4. Make the smallest coherent change that advances the actual requested outcome. Check licensing before candidate reuse. Keep credentials, `.env` files, client models, private project data and generated project outputs out of commits. Stage explicit intended paths and inspect the diff.
5. Verify the affected behavior at its actual scope and run relevant inherited checks when execution is authorized. Record commands, results, exclusions and untested areas. Stop dependent steps after an error or uncertain apply, inspect real state before retrying, and continue safe independent work.
6. Update the relevant feature docs with behavior changes and add a concise entry to [CHANGELOG.md](CHANGELOG.md) for material Greyledge changes. Report files changed, why, proof and remaining uncertainty. A plan or green narrow check does not prove broad functionality.

For repository/documentation setup, verify roots, URLs, GitHub visibility/parents, branch/commit equality, clean status, preserved ancestry and licenses, documentation links and diff scope. Git inspection and whitespace checks suffice for this package; application tests, builds and launches were expressly outside scope. Future implementation needs appropriate behavior validation, not repetition of this setup check.

This setup does not authorize dependency installation, feature work, integrations, application/service execution or enabling inherited GitHub Actions. A later task must establish that scope; dependency installation needs the explanation and user approval specified in the active task. Never describe unrun checks as passing. Correctness and usable project outputs take priority over overengineering.
